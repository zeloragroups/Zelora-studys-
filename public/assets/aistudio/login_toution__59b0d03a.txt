ZELORA STUDYS — UNIFIED STUDENT & TEACHER LOGIN, PREMIUM DARK THEME AND ANIMATED STARTUP EXPERIENCE

PROJECT OBJECTIVE

Upgrade the existing tuition management application into a polished, professional education platform branded as ZELORA STUDYS.

This is an enhancement to an existing working application, NOT a new application. Carefully inspect the existing repository, architecture, authentication implementation, navigation, Firebase configuration, design system, and all existing features before making changes.

The primary objective is to create:

1. One unified login page for Students and Teachers.
2. Automatic role detection using the existing institutional ID and password authentication.

4. A premium, professional dark theme as the default across Admin, Teacher, and Student applications.
5. A fully functional Light Theme option.
6. A professional animated startup/loading screen branded ZELORA STUDYS.
7. A consistent, responsive design experience across mobile, tablet, laptop, and desktop.

The application name must always be written as:

ZELORA STUDYS

Use uppercase letters and bold visual treatment wherever the brand name appears prominently. Do not use the old academy name or any alternative application name.

PART 3 — AUTOMATIC ROLE DETECTION AND REDIRECTION

This is one of the most important requirements.

The application must determine the role using trusted authentication data, not merely the prefix typed by the user.

Authentication flow

1. User opens the unified login page.
2. User enters institutional ID.
3. User enters password.
4. Existing authentication service verifies credentials.
5. The application retrieves the authenticated user's authorised profile.
6. The system verifies the account's active status.
7. The system determines the trusted role.
8. The system loads the correct application.
9. The user is redirected to the correct dashboard.

Student flow

"Login → Authenticate → Verify Student Role → Student Dashboard"

Teacher flow

"Login → Authenticate → Verify Teacher Role → Teacher Dashboard"

Security requirements

- Never trust the client-provided role.
- Never trust an ID prefix as the sole authorization mechanism.
- Never allow a Student to access Teacher routes.
- Never allow a Teacher to access Student routes.
- Do not rely on hidden navigation items for authorization.
- Preserve existing RouteGuard and role-protection logic.
- Revalidate the authenticated account and role when appropriate.
- Reject inactive accounts.
- Reject accounts with missing or invalid role information.
- Do not automatically grant a role based on a missing Firestore field.
- Preserve existing account status and permission checks.

If role verification fails, show a safe error and do not redirect.

Session persistence

Preserve the existing Firebase Authentication session strategy.

On application refresh:

- Check the current authenticated session.
- Verify the user's role.
- Redirect to the appropriate dashboard.
- Prevent unauthorized route access.
- Avoid unnecessary repeated login screens.

When a user signs out:

- Clear the authenticated session using the existing AuthContext sign-out implementation.
- Clear role-specific in-memory state.
- Redirect to the unified Student/Teacher login page.
- Do not leave private dashboard content accessible through browser history.
