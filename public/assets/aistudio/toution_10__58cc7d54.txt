Inspect the existing ID/password authentication service before implementation.

Firebase Authentication must become the trusted authentication provider.

The user-facing login identifier must remain the existing Admin ID, Teacher ID or Student ID.

Firebase Authentication normally uses email/password or custom authentication tokens. Do not pretend that arbitrary IDs can be passed directly to Firebase's email/password sign-in method.

Design and implement a secure ID-based login adapter.

Preferred approach:

- Use a trusted server-side account creation workflow.
- Maintain a secure mapping between application login IDs and Firebase Auth UIDs.
- Use Firebase Authentication for actual password verification.
- Use a controlled internal authentication identifier where required.
- Do not expose account mapping collections to public users.
- Do not allow users to choose or change their role.
- Do not allow client-side assignment of Admin privileges.

If using an internal email alias for Firebase Authentication, derive and manage it consistently through a documented backend strategy. Do not rely on real user email addresses that the user has not supplied.

Do not store plaintext passwords in Firestore, localStorage or browser state beyond the minimum time needed for authentication.

Do not store password hashes in application account documents.

9. ACCOUNT CREATION

Preserve the existing Admin account management workflow.

When Admin creates a Teacher or Student:

1. Validate account details.
2. Generate a unique application ID.
3. Create the Firebase Authentication account through a trusted backend.

5. Create the Firestore profile.
6. Record the creation event.
7. Return the generated application ID to Admin.
8. Display the initial credential only through the intended secure workflow.
9. Never store the initial password in an ordinary Firestore profile or audit log.

Do not create duplicate Auth users if the operation is retried.

Use idempotency and appropriate failure recovery.

If Authentication account creation succeeds but Firestore profile creation fails, handle the incomplete operation safely and provide a recoverable status.

MODULE F — FINANCE AND PAYMENT SECURITY

25. UPI PAYMENT WORKFLOW

Preserve the existing direct UPI payment workflow.

Do not integrate Razorpay or another payment gateway.

Do not connect bank APIs.

Do not claim automated UPI payment verification.

The existing flow must remain:

1. Student chooses full or partial payment.
2. Application prepares a UPI payment link.
3. Student pays through an external UPI application.
4. Student submits transaction reference/UTR.
5. Claim remains pending.
6. Admin independently checks the payment.
7. Admin confirms or rejects the claim.
8. Only a confirmed payment changes the verified paid balance.
9. Receipt is generated only after verification.

A screenshot alone must never mark a payment as successful.

26. PAYMENT SECURITY

Move sensitive verification operations to trusted backend functions.

Validate:

- Payment claim ownership.
- Transaction reference.
- Duplicate UTRs.
- Payment amount.
- Student fee account.
- Current payment status.
- Admin authorization.

Use Firestore transactions to prevent duplicate verification and balance corruption.

A rejected or pending claim must not reduce the student's outstanding balance.

27. RECEIPTS

Preserve existing receipt format and branding.

Receipt generation must be based on verified payment records.

Use unique receipt IDs.

Prevent duplicate issuance.

Preserve historical receipts.

If a verified payment is corrected or reversed, follow an explicit audited correction workflow.

Do not silently edit historical receipt records.

28. TEACHER SALARY

- Duplicate payouts.
